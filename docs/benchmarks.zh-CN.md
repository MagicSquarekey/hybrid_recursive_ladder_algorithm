# 性能基准

**语言 / Languages:** [English](benchmarks.md) · [简体中文](benchmarks.zh-CN.md)

这些数字来自一个生产 AutoTestHub 部署（2026 年 10 月），经 VPN 聚合单条
ThingsBoard 序列。它们是指示性的，不是保证：延迟取决于网络距离、ThingsBoard
负载、数据密度和序列数量。

## 被测量的问题

原实现**每个统计桶发一次查询**：

* 两天分钟级区间 = 1,140 个桶；
* 每个桶最多需要四次 HTTP 请求（聚合 + 边界点）；
* 实测墙钟时间：**139 秒**。

瓶颈是网络往返，不是算术。

## 结果

| 场景 | 段数 | 请求数 | 时间 | 正确性检查 |
|---|---:|---:|---:|---|
| 2 天，分钟级 | 69 | ~4 | 0.64 秒 | 合计 2,217,024.0 = 2,566 个原始点之和 |
| 1 年，日级 | 42 | ~4 | 冷 1.18 秒 / 热 0.20 秒 | 合计 36,012,018.25 |
| 10 个月，混合层级 | 97 | ~5–7 | 亚秒级 | 省掉 423,049 个分钟桶 |
| 本地读，42–90 段 | 42–90 | 0 | 9–19 毫秒 | 一条 SQL |
| 混合读（3 本地 + 1 数据源段） | 4 | 1 | 0.31 秒 | 与纯源合计一致 |
| 校验 + 修复（篡改 1 点） | — | — | — | 发现 1 个变动点，重写 360 点，之后 0 差异 |

10 个月示例把 **423,049 个分钟桶压缩成 97 段**（约 4,360 倍更少的单位）。

## 请求数模型

对于含 `M` 个月、`D` 天、`H` 小时、`N` 分钟的区间：

```
聚合请求数 ≈
    ceil(D_total / max_intervals)      # 月
  + ceil(H_total / max_intervals)      # 日
  + ceil(N_total / max_intervals)      # 时 + 分（共享取数）
  + 1                                  # 不足一分钟的零头（如有）
```

`max_intervals` 默认 500。测试中 ThingsBoard 接受 700 个桶、拒绝 800 个；
文档里常说的 1000 不可靠。

`max_intervals=500` 时的示例：

| 区间 | 最细取数层的桶数 | 请求数 |
|---|---:|---:|
| 2 天，分钟 | 2,880 个分钟桶 | 6（另加一个零头） |
| 1 年，日 | 365 个日桶 | 1 |
| 10 个月，混合 | 约 294 日 + 480 时 + 1,130 分 | 约 6 |

实现会合并共享同一取数层级的相邻 run（时与分），所以观测值常常低于三项之和。

## 本地优先读

固化一个区间后，重复查询读 PostgreSQL：

* 每条序列一条批量 SQL，覆盖所有已覆盖子区间；
* 生产库中 42–90 段耗时 9–19 毫秒；
* 只有未覆盖子区间会打到 ThingsBoard；
* 部分覆盖的段只补缺失的那一截。

三个本地段加一个数据源段的混合读耗时 0.31 秒，合计与纯源查询完全一致。

## 校验与修复

* 篡改一个本地 point（+999）会产生一个差异段，并在预期时间戳发现一个变动点。
* 修复为该区间重写 360 个点；第二次校验报告 0 差异。
* 点级展开默认每次报告最多 50 段，因此大的分歧不会意外触发全量重新下载。

## 不连服务器复现

`examples/benchmark.py` 用一个计数包装器包住内存数据源，运行相同的分解。它
测量的是**段数与请求数**，不是网络延迟，并且是确定性的：

```bash
python examples/benchmark.py
```

预期形态（具体段数取决于所选起止时间；这些区间故意不按月对齐）：

```
range                        segments  agg_requests raw_requests
-----------------------------------------------------------------
2 days, minute                    100             3            0
10 months, mixed levels            97             3            1
1 year, day level                  47             3            0
```

生产环境的 2 天查询是 69 段，因为它的起止时间不同；真正稳定的指标是请求数，
无论区间多长都保持在个位数。

## 注意事项

* 生产数字包含 VPN 延迟；同机部署会更快，高延迟链路会更慢。
* 数据密度影响原始点请求和固化时间，不影响聚合请求数。
* ThingsBoard 版本和配置可能改变桶数上限；适配器的 `max_intervals` 可配置。
* 本地读时间取决于 PostgreSQL 硬件、分区和索引缓存。表结构使用主键
  `(namespace, entity, key, ts)`，因此求和的范围扫描是索引扫描。
