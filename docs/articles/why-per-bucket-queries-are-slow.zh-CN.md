# 1,140 个桶，139 秒：逐桶时序查询为什么慢

一个生产环境的 ThingsBoard 查询，走 VPN，1,140 个统计桶花了 **139 秒**。算术本身很便宜，贵的是网络。

这是一个查询规划器的故事：它把「每个桶问一次」变成「按日历层级问几次」，请求数从几千降到个位数。

## 那个查询

客户端要一个长区间的分钟级聚合。旧实现每个统计桶问一次数据源，每个桶最多 4 次 HTTP：一次聚合，加上边界点。

1,140 个桶，最多就是 4,560 次往返。走 VPN，每次几十毫秒，139 秒很合理。完整两天的分钟级是 2,880 个桶；生产环境那个区间恰好小一些。

第一反应通常是优化算术。但算术从来不是瓶颈。

## 三种显而易见的修法，为什么都不够

**1. 整段只取一个粗粒度桶。** 一次请求就够，但每分钟/每天的行没了，而输出粒度正是产品本身。

**2. 预聚合。** Continuous aggregate、rollup 表、多分辨率存储都能解决——前提是你能控制数据库。只读遥测 API 通常不让你建物化视图，也不让你改保留策略。

**3. 分页。** 分页减小页大小，不减少页数；而且每个分页边界都是一个新的「点重复/丢失」风险点。

真正有用的问题是：**数据源能不能对一段连续区间返回更粗或更细的聚合，让一次请求填满很多输出单位？** 对大多数区间聚合 API，答案是能。

## 日历阶梯

输出需要每个完整日历单位一个值，但数据源不需要每个输出单位一次请求。把这两件事分开，就是 ladder 的核心。

### 1. 按完整日历单位分解

把 `[start, end)` 从月到分递归切开：

- 每一层只输出完整包含在区间里的单位；
- 不完整的左、右残段交给下一层；
- 最细层的不足一分钟残段作为零头单独成段。

对 `2026-01-01 00:00:00 → 2026-10-21 18:49:59`：

```
月    2026-01 … 2026-09          9 段
日    10-01 … 10-20             20 段
时    10-21 00:00 … 17:00       18 段
分    10-21 18:00 … 18:48       49 段
零头  10-21 18:49:00–18:49:59    1 段
                                ─────
                                97 段
```

97 个输出段，而不是 423,049 个分钟桶。但更重要的数字是请求数：**5–7 次聚合请求**，不是几千次。

### 2. 每层用下一级更细的聚合抓取

输出层决定输出粒度，不决定取数粒度：

| 输出层 | 取数层 | 原因 |
|---|---|---|
| 月 | 日 | 多数数据源没有自然月 interval，拉日级再折叠 |
| 日 | 时 | 避开固定桶导致的日边界漂移 |
| 时 | 分 | 把精确的分钟折成小时 |
| 分 | 分 | 直接取分钟 |
| 零头 | 原始点 | 区间桶无法表示不足一分钟的段 |

月段问日桶再求和，日段问小时桶，时段问分钟桶。折叠在本地做。

### 3. 按「取数层级 + 连续性」分组

这是最容易写错的地方。相邻段只有在**取数层级也相同**时才能合并成一个 run。

- 小时段和分钟段都按分钟取数，可以共用一个 run；
- 月段按日取数，日段按小时取数，不能共用。

如果只按相邻分组，多层级区间会被整体按最粗层取数：一整天的值被塞给第一个小时，后面的小时/分钟全错。原实现里这是一个真实的正确性 bug，不只是性能问题。

### 4. 本地折叠

把返回的桶按起点归到输出段里求和。数据源负责长区间上的重聚合，客户端只做少量桶的轻折叠。

## 请求数上界

设 `K` 是数据源单次请求允许的最大桶数。对一个时长为 `T`、取数桶长为 `Δ` 的 run，适配器按 `K * Δ` 分窗：

```
requests(run) = ceil(T / (K * Δ))
```

总请求数是所有 run 之和。常见的连续情形最多三个聚合 run（日、时、分），所以最多三项。

10 个月示例，`K = 500`：

```
月        -> 按日取数：  273 个桶 -> 1 次请求
日        -> 按小时取数：480 个桶 -> 1 次请求
时 + 分   -> 按分钟取数：1,129 个桶 -> 3 次请求
R_agg ~= 5
```

结构上的原因是：细粒度工作只发生在两端的残段里。对默认层级：

```
N_day    <= 2 * 31 = 62
N_hour   <= 4 * 24 = 96
N_minute <= 8 * 60 = 480
tail     <= 1
N <= N_month + 639
```

递归深度不超过层数（4）。十年的区间不会炸成分钟桶；它大约是每个月一段，加上有界的边角工作。请求数按 `O(N_month / K + 1)` 增长，而不是按分钟桶数增长。

## 本地优先读

有本地点存储时，同一套分解还能这么用。每个输出段先按覆盖区间切成已覆盖/未覆盖：

1. 已覆盖部分用一条批量 SQL 求和；
2. 完整未覆盖的段走分组聚合；
3. 部分覆盖的段只补缺的那一截；
4. 段值 = 本地部分 + 数据源部分。

在生产部署里，42–90 段的本地读是 9–19 ms；三个本地段 + 一个源段的混合读是 0.31 秒，合计与纯源查询完全一致。覆盖只记录到 `now - grace`，重写前先失效，所以拉取失败会重拉，而不是信任不完整的本地数据。

## 这不是什么

这是一个查询规划组合，不是新的通用聚合理论。每一块都有先例：

- **RRDtool / Whisper**：多分辨率归档与 consolidation；
- **BTrDB**：时间分区树 + 每节点统计；
- **TimescaleDB 层级连续聚合**：分钟 → 小时 → 日；
- **Apache Druid period granularity**：带时区的日历经度桶；
- **Prometheus / Grafana**：点数上限 + 单粒度降采样；
- **线段树**：规范对齐区间分解；
- **层级时间轮**：层级 + 余数 cascade。

具体贡献是组合：把日历层级当作查询计划、按下一级更细抓取、按取数层级分组、按覆盖补缺口，并在每请求桶数上限下规划请求。方法已经作为[公开披露](../defensive-publication.md)发布，代码是 MIT。

## 什么时候用

适合：

- 你能读区间聚合接口，但不能写源端、不能改源端存储/降采样策略；
- 数据源有每请求桶数/点数硬上限；
- 输出是日历形状（月、日、时、分）；
- 你能接受本地折叠和文档里说明的 DST 限制；
- 你想做本地缓存，但不想改数据源。

不适合：

- 你能控制数据库：直接用 continuous aggregate 或多分辨率存储；
- 你需要精确的 `avg`、分位数或 meter delta：当前版本只实现 `sum`；
- 你需要在 DST 切换点做到精确的亚分钟行为：用原始点或更细的取数层；
- 数据源根本没有区间聚合接口。

## 复现

```bash
pip install https://github.com/MagicSquarekey/hybrid_recursive_ladder_algorithm/releases/download/v0.0.4/hybrid_recursive_ladder-0.0.4-py3-none-any.whl

hybrid-ladder demo
hybrid-ladder decompose --start 2026-01-01 --end 2026-10-21T18:49:59
python examples/benchmark.py
```

benchmark 不需要服务器，只打印段数和请求数。

## 结论

如果你的时序 API 按请求计费、或者限制每请求桶数，那么**往返次数就是设计变量**。你不一定需要一个新的数据库；有时候只需要停止「每个输出行问一次」，开始把区间当成日历来规划。
